Latency optimization audit
==========================

Objective: reduce all measured latency paths until further gains require a
correctness, resource, behavior, or compatibility compromise. This audit is
ongoing; the completed work below does not establish that the objective is met.

Preserve cell rendering, Unicode fallback, selection and IME behavior; live
session ownership and explicit legacy rollback; desktop integration; calling
shell configuration; and bounded CPU, memory, queues, and output batching.
Do not remove these costs merely to improve a benchmark number.

Measurement entry points
------------------------
manage.py latency-visible: fresh/additional window mapping and visible readiness,
plus real XTest key events through a PTY to observed pixels. Snapshot/compare
alternates matched workloads. Private Xvfb excludes desktop compositor, physical
keyboard, and monitor scanout; observation adds a polling/readback allowance.

manage.py frame-perf: ordinary paced PTY output to a complete service frame,
without keyboard-response boosting. Report latency, delivered frame count,
daemon CPU counter resolution, and RSS/PSS; compare a frozen daemon snapshot.

manage.py preview-perf: fresh launch/interactive-shell/input timings and
helper-inclusive memory. check-preview also times dense full/row painting.

Remaining audit scope includes GTK presentation after service delivery, dense
painting, view/tab switching, scrolling, and fresh GTK/shell startup. Compare
CPU/memory and validate visual/input/session invariants before accepting changes.

Verified checkpoint: output scheduling
-------------------------------------
The service used a fresh 16 ms sleep even when its existing deadline was near.
It now waits only the remaining interval; both the wait and emission condition
use the same policy. The configured batching limit and input boost are unchanged.

A 40-response native-protocol comparison measured 7.93/16.30 ms median/p95
before and 1.96/2.37 ms after. All responses arrived in both runs. Delivered frames
increased from 61 to 81 because fewer intermediate states were coalesced by the
oversleep; the rate cap was not raised. Daemon PSS measured 253/249 KiB and
CPU below the 10 ms accounting resolution in this workload, rather than a claim
of literally zero processing cost. Frozen samples remain under
.checks/frame-deadline-verified-{baseline,candidate}.json.

Faster delivery exposed early-output correctness failures. Pending-wrap cursor
mapping across width changes and pending-wrap preservation on unchanged-width
resizes are now covered by native regressions. The existing counterfactual proof
command verifies that restoring the old mapping fails. Local and SSH GTK checks
pass with corrected cursor handling and the new output deadline policy.

Follow-up: visible launch/input comparison is not yet conclusive
---------------------------------------------------------------
Ten alternating pairs with twenty keystrokes each measured candidate/baseline
typing medians of 3.80/3.97 ms and p95 of 11.65/8.63 ms. Additional-window visible
readiness medians were 51.78/35.60 ms, with a +25.42 ms paired median difference.
Fresh-window paired readiness was -17.90 ms despite higher candidate marginal
medians, demonstrating substantial variation within the run. These results do
not establish an overall launch/input improvement or rule out a presentation
regression. Investigate this before declaring the full objective complete.
Frozen data: .checks/latency-goal-post-schedule.json. The installed build has not
been replaced by this checkpoint, and live daemons have not been restarted.

Follow-up control and renderer checkpoint
-----------------------------------------
Twenty identical-binary pairs produced additional-window readiness medians of
9.19/24.38 ms, yet their paired median difference was only -1.65 ms. Marginal
medians alone are therefore unreliable for this frame-clock-sensitive probe.
Frozen data: .checks/latency-aa-control-comparison.json.

A quieter twenty-pair repeat against the pre-scheduler build measured a paired
additional-window difference of +1.78 ms, rather than the earlier +25.42 ms.
Fresh readiness remained +9.79 ms in paired samples. The large additional-window
regression did not reproduce; fresh presentation still needs investigation.
Frozen data: .checks/latency-scheduler-repeat.json.

GTK backgrounds now combine consecutive equal-color cells into runs on aligned
device grids. Fractional transforms retain scalar fills to preserve antialias
and alpha-edge behavior. Color/cursor decisions share one policy, and every
background is still painted before any glyph ink. No pixel buffer/cache is added.

Exact scalar-reference comparisons pass for mixed colors, reverse cells,
transparency, clipping, integer scaling, and fractional transforms. Existing
clipped-glyph, selection, IME, ownership, browser and SSH integration checks pass.
Sixty alternating same-process measurements reported scalar/spans background
means of 3.28/0.41 ms in one run and 12.62/1.90 ms under heavier load in another.
This establishes lower background work, not a claimed 7x whole-frame speedup.

Launch-focused follow-up
------------------------
Deferring the empty tab strip's Pango layout until its first catalog refresh
removes unnecessary pre-map setup. Twenty alternating candidate/baseline pairs
measured fresh readiness medians of 99.28/101.20 ms, paired median -2.41 ms;
mapping paired median was -2.57 ms. Additional-window paired readiness was
-0.10 ms. Frozen data: .checks/launch-lazy-tabs-experiment.json. Local and SSH
integration checks pass, including an assertion that mapping an empty window
has not initialized its tab layout.

An experiment painting the first complete frame synchronously showed no gain
(fresh readiness paired +0.38 ms, additional +0.13 ms) and was discarded.
Frozen data: .checks/launch-first-frame-experiment.json.

Saved-tab launch work
---------------------
Unviewed terminal proxies no longer allocate st cell buffers merely because a
catalog lists them. First use allocates the requested geometry; a first incoming
frame allocates its validated geometry without loading fonts. Rows before any
frame are ignored. Tests cover unprepared destruction, first-use dimensions,
and unmapped first-frame allocation, alongside full local/SSH integration.

The visible benchmark now accepts --saved-tabs and records process-tree frontend
memory through the existing shared metrics. It seeds real PTYs in private service
scopes and leaves live desktop sessions untouched. Its typing probe calibrates
expected glyph images outside measured keystrokes: the earlier any-pixel-change
test could mistake a late resize for an echo, particularly with large catalogs.
X11 discovery also tolerates windows destroyed after its root-tree snapshot.

Command: python3 manage.py latency-visible --compare .checks/launch-focus-baseline
         --saved-tabs 100 --trials 20 --keys 10
Candidate includes lazy strip layouts and lazy cells; baseline is f5761db.
Fresh visible readiness median: 93.06 vs 103.91 ms, paired median -8.79 ms.
Additional-window readiness: 28.07 vs 41.72 ms, paired median -11.15 ms.
Frontend PSS median: 16827 vs 25192 KiB, measured after typing and before the
additional window. Typing medians: 2.57 vs 2.55 ms; p95: 5.31 vs 4.56 ms.
This is launch and memory evidence, not an input-latency improvement claim.
Frozen data: .checks/launch-saved-tabs-verified.json. Private Xvfb excludes
desktop compositing and physical scanout; filesystem caches are warm.

A twenty-pair run without seeded tabs measured fresh readiness 100.30/102.03 ms,
paired -1.20 ms; additional readiness paired +0.14 ms. The benefit is largest
with populated workspaces. Frozen data: .checks/launch-unseeded-verified.json.
The updated full local/SSH GTK suite passes. Lint file-size/line-length checks
pass, but Clang analysis cannot run because clang-tidy is not installed.

Installed a7ab3cf with the configured Alacritty theme. Installed launcher,
frontend module and daemon match the verified build. Existing GTK owners keep
their loaded frontend until all their windows close; live daemon sessions were
not restarted or migrated.

Idle presentation work
----------------------
Blink ticks previously requested full-widget damage every 800 ms, even with a
steady/hidden cursor and no blinking text. They now damage only rows containing
blinking glyphs or a visible blinking cursor, and skip unmapped views entirely.
The blink phase still advances while hidden; no visible blink behavior is removed.

Catalog palette, reverse-video, cursor shape and cursor visibility changes now
invalidate their own pixels. Palette changes repaint the active tab strip too.
This is required because the old blanket timer repaint could otherwise conceal
missing metadata-only damage. Palette comparison uses parsed RGBA values, so
unchanged catalogs do not introduce new repaints.

The real GTK damage regression disables its automatic timer, explicitly invokes
20 ticks with a steady cursor and 20 with a hidden cursor, and observes zero
draws. It verifies partial draws for blinking cursor/text, full draws for palette
and reverse changes, no damage for unchanged metadata, and no hidden-view draws.
Full local and SSH integration checks pass. This proves reduced idle paint work;
it is not yet evidence of a reduction in end-to-end typing latency.

Interaction presentation probe
-------------------------------
manage.py interaction-perf now measures first tab ownership claim, cached tab
switches after warm-up, wheel scroll and Shift+PageUp/PageDown. Each trial uses
a fresh private display/workspace with two native fixtures. Known background
colors distinguish the expected tab and scrollback/live rows; the observed
window is raised so obscured-window pixels cannot satisfy the probe.

The existing native echo fixture accepts an explicit RGB background and an
optional bounded history producer. Default typing/launch behavior is retained.
The root benchmark reuses launch, polling, screenshot diagnostics, keyboard
injection and process resource helpers. --compare alternates variant ordering.
No desktop windows or live workspaces are used.

A two-trial smoke run observed cached switch/wheel/page medians around 16.6 ms
and first-claim median 22.46 ms. This identifies a frame-clock interval worth
investigating, rather than establishing an optimization claim.

Ten alternating identical-application control pairs confirmed the probe:
candidate/baseline cached-tab medians 16.77/16.86 ms, wheel 16.63/16.70 ms,
page 16.42/16.70 ms, first ownership claim 25.27/24.84 ms. Each version has
200 samples per cached/scroll path and ten first claims. Frontend CPU counters
for the measured interaction loops range 0.12--0.17 seconds per trial, with
10 ms accounting resolution. Frozen data: .checks/interaction-aa-control.json.

The current interaction probe is self-paced: each request waits for its visible
result before sending another. Before accepting scheduling changes, distinguish
isolated first-response latency from sustained streams and verify that faster
presentation does not introduce unbounded painting or lose output batching.
Cached views must also avoid synchronously painting partially imported frames
or geometry belonging to a previous owner. These remain open audit requirements.

Installed a3ae3c8, including the idle redraw fix and explicit metadata damage.
The installed launcher, frontend and browser modules match the verified build;
live owners and daemon sessions were preserved. This checkpoint does not close
the remaining presentation, dense-paint, startup and resource audit.

First ownership-claim presentation
----------------------------------
Explicit terminal selection now reserves one early-paint allowance when a new
ownership/geometry response is needed after a quiet display refresh interval.
The allowance is consumed only by a changed, complete service frame whose
geometry matches the mapped terminal. Unchanged metadata, individual rows and
old geometry do not trigger early presentation. Cached tab mapping schedules
its usual GTK draw; rapid selections retain GTK batching. Only the terminal's
window updates are processed, reusing the established keyboard-response path.

The interaction benchmark now accepts --pace-ms, records actual paint callbacks,
and exercises a 100-event wheel burst with requested 2 ms spacing. Delays are
outside measured latency. Claim CPU accounting includes a 50 ms drain and uses
both coarse process counters and main-thread scheduled runtime from schedstat.
The latter resolves work below the process counter's 10 ms ticks, but does not
measure other threads. The benchmark logs resource scope and raw observations.

Ten alternating pairs with 20 samples per cached/scroll path measured candidate
versus baseline first-claim medians of 5.94/22.99 ms and p95 of 9.20/26.70 ms.
Each version made a median three terminal paint calls during the claim window.
Main-thread claim runtime medians were 3.92/4.75 ms. Interaction-loop paint counts
were 60/60, with process CPU medians 155/160 ms. The fixed-input wheel burst made
14/14 median paints, with coarse CPU medians 65/60 ms; the 5 ms median difference
is within the process counter's 10 ms granularity, not proof of zero difference.
Cached switch, wheel and page medians remained about 16.6--16.9 ms in self-paced
loops. Frozen final comparison: .checks/interaction-claim-verified.json.

Rejected experiments remain informative. Eager cached-tab painting added ten
paints to a 30-interaction paced workload without improving latency. Early
scroll painting slightly improved self-paced scroll medians but added a median
paint to a fixed wheel burst; isolated paced scrolling already measured around
3.7 ms. Both changes were removed. Frozen experiments:
.checks/interaction-first-experiment.json and
.checks/interaction-scroll-experiment.json. Root-wide early claim painting was
also replaced by the existing terminal-only update path; its earlier comparison
is .checks/interaction-root-claim-experiment.json. These are experimental results,
not evidence that the discarded behavior remains enabled.

The final source passes the full local and SSH X11 integration suites, including
explicit assertions that selection does not synchronously paint cached/partial
cells, incomplete frames and mismatched geometry retain their allowance, and a
complete changed response consumes it. Unchanged metadata still preserves the
keyboard allowance. File-size/line-length checks pass; clang-tidy is unavailable.
The native Wayland command cannot start: the project-local Weston runtime is
absent and the harness targets Weston 10, while available packages use Weston 16.
Native Wayland validation remains open; this is an environment/harness gap, not
a passing compatibility result.

A final 20-pair launch/input check against the same snapshot measured paired
fresh/additional readiness differences of -1.67/-0.20 ms. Typing median/p95
were 2.91/4.41 ms versus 2.79/4.13 ms, with one candidate maximum of 9.80 ms.
This is not an input-latency improvement claim. Frontend PSS medians were
11950/11974 KiB. Frozen data: .checks/claim-launch-input-verified.json.

Installed c7d65a7 with the existing Alacritty theme. Launcher, frontend and
browser module byte comparisons match the verified build. Live GTK owners and
daemon sessions were preserved; a new GTK owner loads this frontend. Remaining
work includes native Wayland coverage and the wider latency/resource audit.

Native Wayland coverage restored
--------------------------------
manage.py setup-preview-wayland now supports the audited Weston 10 and 16 seat
ABIs. It downloads into a fresh project-local package directory, extracts each
ABI into its own runtime tree, and publishes the selected runtime after package
extraction. Old package archives cannot be silently mixed into a new setup.
The test module uses matching headers and a per-ABI output, tracks header and
runtime-selection dependencies, and rejects mixed or mismatched layouts.
Both current /usr/libexec and legacy shell-helper locations are supported;
the private compositor's input-method helper uses the same selected runtime.
The explicit WORMINAL_WESTON override and legacy runtime layout remain available.

The real Weston 16 compositor now runs the entire GTK/WebKit suite natively,
locally and through the SSH fixture. DISPLAY is absent and the test asserts the
GDK Wayland display type; there is no X11 fallback. Recent idle damage, completed
claim-response painting, clipping, font caches, selection, IME, browser ownership
and recovery checks all pass. The idle assertion first waits for startup paint
activity to quiesce, then still requires zero steady/hidden-cursor blink redraws.
This fixes the observer's startup assumption rather than weakening the invariant.

manage.py check-headless passes, including four new runtime/build regressions
for ABI selection, shell-helper paths, mixed/mismatched headers, stale package
exclusion and failed-download preservation of the previous selection. Full local
and SSH X11 checks also pass. Weston 10 layout compatibility is covered by those
unit fixtures; this machine's actual native compositor run uses Weston 16.
File-limit checks pass; Clang analysis is still unavailable without clang-tidy.

An initial native run measured dense full paints at 12.12/12.09 ms and input
callback to GTK paint at 4.38/4.31 ms (local/SSH, mean of 20 echoes for input).
These are rendering/callback measurements, excluding physical key delivery and
compositor presentation; they are not native key-to-visible-pixel measurements
and do not demonstrate a new performance improvement. Dense foreground work
and native presentation remain part of the wider latency audit.

Native test clients pass, but the private compositor logs a layer-finalization
warning during teardown. Its cause and shutdown status have not been audited;
this remains a harness validation limit, not a passing absence-of-warnings claim.

Cached ASCII drawing
---------------------
Cached printable ASCII layouts now draw their single Pango line at that layout's
own baseline. Bold/italic and fallback metrics are retained; other strings keep
the full-layout path. This adds no glyph cache or persistent per-view state.

The new manage.py render-perf command loads the actual release frontend module
and imports dense ASCII, mixed Unicode, and a clipped ASCII stripe through the
real terminal packet API. GTK draws the real widget into Cairo images. It checks
exact RGBA hashes and geometry across variants, alternates order, excludes 20
warm-up frames per case, and records wall time, CLOCK_PROCESS_CPUTIME_ID CPU,
and PSS with the shaped layouts alive. Snapshots need a compatible internal
frontend view ABI. This measures rendering, not input or display presentation.

Ten alternating pairs, 60 measured frames per case, gave these median CPU costs
in milliseconds per frame (candidate / previous full-layout implementation):

  backend   dense ASCII     mixed Unicode    clipped ASCII
  X11       6.652 / 7.432   8.447 / 9.347    0.990 / 1.153
  Wayland   7.257 / 7.933   8.442 / 9.292    1.049 / 1.142

These workloads reduce repaint CPU by about 8--14%. Every rendered image matches
the baseline exactly. PSS medians were 46366/46427 KiB on X11 and 20175/20181 KiB
on Wayland, providing no evidence of a memory increase in this workload.
Frozen reports: .checks/ascii-line-release-{x11,wayland}-verified.json. Reports
record the loaded module hashes; native runs assert Wayland with DISPLAY absent.

Independent legacy Pango layouts also verify all 95 printable ASCII glyphs and
four font styles against the production path, before and after zoom, in LTR/RTL
contexts, with transparency, clipping, integer scaling and fractional transforms.
Full local/SSH X11 and native Wayland integration suites pass. File-limit checks
pass; clang-tidy remains unavailable. The initial new release probe caught a
buffer ownership bug in its own fixture, fixed by clearing consumed buffers;
no product state or live session was involved.

The final 20-pair visible comparison measured fresh readiness 99.78/99.23 ms,
with paired median +0.15 ms; additional readiness paired -0.79 ms. Typing median
and p95 were 2.96/4.27 ms versus 3.06/4.35 ms. This does not establish a separate
end-to-end typing improvement. Frozen data: .checks/ascii-line-input-launch-verified.json.
