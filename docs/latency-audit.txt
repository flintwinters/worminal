Latency optimization audit
==========================

Objective: reduce all measured latency paths until further gains require a
correctness, resource, behavior, or compatibility compromise. This audit is
ongoing; the completed work below does not establish that the objective is met.

Preserve cell rendering, Unicode fallback, selection and IME behavior; live
session ownership and explicit legacy rollback; desktop integration; calling
shell configuration; and bounded CPU, memory, queues, and output batching.
Do not remove these costs merely to improve a benchmark number.

Measurement entry points
------------------------
manage.py latency-visible: fresh/additional window mapping and visible readiness,
plus real XTest key events through a PTY to observed pixels. Snapshot/compare
alternates matched workloads. Private Xvfb excludes desktop compositor, physical
keyboard, and monitor scanout; observation adds a polling/readback allowance.

manage.py frame-perf: ordinary paced PTY output to a complete service frame,
without keyboard-response boosting. Report latency, delivered frame count,
daemon CPU counter resolution, and RSS/PSS; compare a frozen daemon snapshot.

manage.py preview-perf: fresh launch/interactive-shell/input timings and
helper-inclusive memory. check-preview also times dense full/row painting.

Remaining audit scope includes GTK presentation after service delivery, dense
painting, view/tab switching, scrolling, and fresh GTK/shell startup. Compare
CPU/memory and validate visual/input/session invariants before accepting changes.

Earlier checkpoint evidence is preserved in docs/latency-history.txt.

First-content presentation experiment (rejected)
-------------------------------------------------
A one-shot allowance was evaluated for newly created terminals: retain it over
blank/unchanged frames, detect imported glyph/background/decorative content,
and process updates only after complete mapped geometry-matching frames. This
would reuse the existing keyboard/claim early-paint mechanism without eagerly
painting later bulk output. It is NOT retained in the source or installed build.

Ten paired minimal-fixture trials measured fresh readiness 99.56/99.80 ms,
paired -1.04 ms, and additional readiness 27.48/26.54 ms, paired +0.58 ms.
Five traced zsh pairs measured fresh/additional paired +1.59/+0.31 ms. The
experimental startup-paint marker fires, but early setup content can consume
it long before usable shell output: additional median allowance use 33.90 ms,
last complete frame 111.13 ms, last paint 111.49 ms, readiness 115.52 ms.
There is no demonstrated useful-launch gain to justify the content heuristic
and extra synchronous-paint opportunity. Frozen experiments:
.checks/first-content-minimal-experiment.json,
.checks/first-content-shell-rejected.json and corresponding .log. Rebuilt
frontend.so is byte-identical to .checks/first-content-baseline/build/frontend.so.

First-ready frontend resource accounting
-----------------------------------------
latency-visible --startup-resources adds an optional snapshot after the fresh
window's unique ready pixels appear. It records observed live frontend/helper
per-process CPU, main-thread scheduled runtime, VmRSS and approximate VmHWM.
Whole-process CPU uses Linux clock-tick counters; main-thread scheduled runtime
resolves smaller differences but excludes non-main threads. Exited helpers and
daemon-owned PTY shells are outside the sample. Separate process high-water
marks are not simultaneous peak RSS, and no whole-application peak PSS claim
is possible from this mode. Sampling can perturb subsequent timing; independent
untraced/resource-free pixel measurements remain the primary latency evidence.

The new regression touches and releases 32 MiB in a child, verifying the
high-water observation survives the allocation while current RSS falls by a
large margin, and CPU counters remain monotonic. An initial exact inequality
between pre-release VmRSS and later VmHWM failed by 172 KiB; Linux documents
both status counters as approximate. The test now checks the large known
allocation rather than imposing an invalid exact ordering. See primary docs:
https://man7.org/linux/man-pages/man5/proc_pid_status.5.html
Headless tests and file/line limits pass; clang-tidy remains unavailable.

Twenty paired real-zsh first-ready resource trials against the earlier worker
baseline measured installed candidate / baseline: approximate frontend VmHWM
medians 32194/32186 KiB, main-thread CPU 82.66/80.30 ms, and process CPU 90/80 ms.
The last difference must not be read as ten milliseconds of resolved extra
work: those counters have ten-millisecond granularity here. Fine main-thread
counters indicate a much smaller difference, while still omitting other
threads. These observations do not prove identical startup CPU or whole-app
resource costs. Fresh readiness remained 143.18/182.21 ms, paired -38.95 ms;
this diagnostic run is supplementary to the previous resource-free trials.
Frozen .checks/first-ready-resources-shell.json. Product artifacts and installed
rendering behavior remain unchanged; resource/presentation optimization is open.
Three additional delayed-bridge pairs verify observed first-ready frontend and
helper membership: every sample includes both processes. Frozen
.checks/first-ready-resources-bridge.json. This is a fixture/accounting check,
not a separate speedup claim or a measurement of real SSH authentication.

Direct cached ASCII glyph strings
---------------------------------
Eligible cached ASCII now draws its already-shaped PangoGlyphString with the
font selected by Pango, retaining the layout's baseline. Eligibility requires
one horizontal, unattributed run with a real font, no centered baseline and no
run offsets. Other cached runs retain line drawing; Unicode/preedit retains
full-layout rendering. Layout ownership and cache invalidation are unchanged;
there is no additional per-view cache, allocation or persistent state.

Pango's public run-offset fields were verified in the authoritative 1.50.0
header and absent in 1.48.10. The implementation compiles this optimization only
with Pango >=1.50; older builds retain their existing line path. Historical
headers were inspected, not full older-runtime integration tests. Sources:
https://download.gnome.org/sources/pango/1.48/pango-1.48.10.tar.xz
https://download.gnome.org/sources/pango/1.50/pango-1.50.0.tar.xz
https://docs.gtk.org/PangoCairo/func.show_glyph_string.html

One-grid imported GTK replicas
-------------------------------
The GTK frontend formerly constructed complete parser sessions for imported
cells. They allocated an unused alternate screen and passed incoming viewport
width changes through owner-side reflow. A new regression with three wrapped
rows proves this invents local history when the authoritative server has already
reflowed the viewport. The original constructor fails the no-local-history
assertion; the frozen counterexample is .checks/replica-parser-counterexample.log.

GTK now explicitly constructs a view-only TermSession with one cell grid. It
pads/crops imported geometry without reflow or history, preserves valid selection
semantics, and leaves alternate-screen content as metadata over the imported
grid. Shared session registration and grid cleanup reuse the existing lifetime
machinery. Parser owners and the legacy X11 constructor retain ordinary
initialization and reflow. Replicas cannot be exported as complete parser
snapshots; normal native snapshot and wire formats are unchanged.

The sanitizer-backed native regression checks top-left cell preservation,
blank growth, dirty rows, word copy, selection across height and alternate
geometry changes, remote scroll metadata, snapshot refusal, context restoration
and 100 repeated one-cell/large-grid transitions. Full headless, local/SSH X11
and native Wayland integration suites pass. The existing counterfactual proof
command also restores the old parser-backed constructor and requires this
invariant to fail (.checks/replica-regression-proof.log). Shared native-test
support sources now have one authoritative build list. The parser monolith's
line limit is preserved rather than raised.

check-handoff --baseline .checks/replica-grid-baseline/worminald adds old-to-new
and new-to-old v2 transfers to the existing four v1/v2 combinations. All pass,

Repeatable startup syscall localization
---------------------------------------
manage.py profile-startup now wraps the existing visible-readiness fixture with
strace on a fresh private Xvfb display/workspace. --shell includes the same
interactive initialization used by latency-visible. It records raw syscall
traces, optional startup milestones, the actual window-owner PID (not the
tracer PID), Unix-nanosecond readiness cutoff and relevant GTK initialization
environment. The optional launch prefix defaults empty for ordinary measurements.
strace follows private threads/children and uses --kill-on-exit; its trace tree
and isolated service are cleaned up without touching any live workspace.

Raw and interactive-zsh profiling both pass. Traced readiness is approximately
437 ms and 1649 ms, respectively, versus untraced roughly 100/144 ms: tracing is
substantially perturbing and these are not latency benchmarks. Raw output also
contains teardown, so filter at the manifest readiness cutoff. Verified raw
artifacts .checks/startup-{profile,syscalls,milestones}-raw-final.{json,log};
shell artifacts use the corresponding -shell-verified names. The manifest's
trace/milestones fields identify the ordinary latest-run filenames; frozen
copies above preserve each observation together.

The trace identifies GTK loading XApp integration and IBus, substantial GTK and
Fontconfig file activity, and configured theme resources before presentation.
Final raw manifest records GTK3_MODULES=xapp-gtk3-module and GTK_IM_MODULE=ibus.
Removing these integrations or substituting the user's theme is a behavior
tradeoff, not an established transparent launch optimization. Syscall counts
or traced elapsed time alone do not establish their untraced critical-path cost.
Further product work needs that distinction; no runtime change is made here.

Full headless checks and both raw/shell profiler modes pass. Two ordinary
untraced launch/typing trials also pass after adding the optional prefix. The
file-limit gate caught the accumulated audit exceeding 1000 lines; older evidence
was moved intact into linked latency-history.txt. Both files are below the cap.
File/line gates now pass; clang-tidy is still unavailable. Product code and
installed artifacts remain at the previously verified a32931f checkpoint.

Cold browser module linking
---------------------------
The optional main-thread CPU sampler attributes much of first browser startup
CPU to ld.so symbol lookup and relocations, followed by graphics/font startup.
WebKit eagerly binds its own imports. Changing g_module_open's lazy flag cannot
remove that work. The frontend previously made its entire GTK dependency group
global solely so browser actions could resolve app_* and wire_* functions.

Browser ABI 3 now carries explicit host callbacks. Navigation state and wire
serialization belong to the frontend; the browser reports URI changes through
that boundary. Both modules load in local scope, avoiding the global GTK search
prefix while loading WebKit. Frontend exports retain only the entrypoint and
release-renderer probe API. Ctrl+K still creates its URL entry on demand.
No background engine, prewarmed process, discarded profile, disabled sandbox or
weakened relocation protections are introduced.

Seven alternating initialized-profile cold HTTP launches on private Xvfb gave
candidate/baseline medians 1052/1234 ms. Frontend main-thread CPU medians were
213/226 ms; total frontend CPU 230/250 ms. Machine scheduling and network-mounted
fixture storage add substantial variance; the 181 ms wall-time difference is not
a portable speedup promise. Earlier isolated deep-binding diagnostics were not
retained in production. Applying settings at WebView construction regressed and
was discarded. Full local/SSH preview behavior and headless checks pass, including
loading both modules with local scope and rejecting leaked frontend callbacks.
Nine all-target pairs gave HTTP 1004/927 ms, file 914/1127 ms and directory
829/945 ms (candidate/baseline). Frontend main-thread CPU fell on every target:
205/236, 215/231 and 218/233 ms. Those wall times remain noisy, with mixed HTTP
results. Three diagnostic CPU-sampled pairs reduced median frontend loader
samples from 74 to 59 and total main-thread samples from 200 to 183.

After behavioral checks finished, eleven uninstrumented HTTP pairs gave 601.07/
638.54 ms median and 650.47/729.77 ms maximum: about 37 ms (5.9%) faster median.
The baseline predates both the lazy location entry and local module callbacks;
these numbers measure their combined effect. Profile storage is initialized,
all application/helpers/service processes stop between trials, filesystem caches
are warm, and desktop compositing/physical display are excluded. Results are
frozen under .checks/browser-cold-{final,all-targets,cpu-samples}.json. Main
checkout headless checks also pass with the unrelated launcher changes retained.
The installed running application is not replaced or restarted by this checkpoint.
